# Swarm Search and Rescue

One victim, one clue, up to eight drones: one brain flies them all.

Swarm Search and Rescue (`cf_swarm_sar`) is the team version of Search and Rescue. One policy controls 2–8 drones that lift off from separate pads, share one noisy search clue, and sweep the map together. The mission succeeds the moment **any one drone** finds the victim and holds a steady confirmation hover above them, without ever touching them. Everyone scores together: one shared team score, identical for every drone. The family is active and carries **0.20** of subnet emissions.

<!-- io-tables:end -->

The leading `dynamic` axis is the drone count `n` (2–8). Each observation key is assembled per drone and stacked, so one `act(obs)` call sees the whole team and must return `n × 6` action values.

**Depth** is always on: a forward-facing metric depth image (same camera pose as RGB: +0.13 m forward, +0.05 m up), PyBullet depth converted to meters, clipped to [0.5 m, 30 m], then scaled to [0, 1]. SAR families render at 256 px with a 30 m far plane.

**RGB is on-demand and budgeted.** A drone's RGB frame is all zeros unless its *previous* action set `rgb_request > 0.5`, and each drone has a per-episode budget of **40** RGB requests. The frame comes from a forward-facing camera (offset +0.13 m forward, +0.05 m up), rendered with the same seeded lighting and FOV as depth (90° ± 2° per map), 30 m far plane. Frozen drones get no frame.

## State vector layout

Each row of `state` is 214 floats describing that drone, in this exact order:

| Index | Channel | Meaning |
|---|---|---|
| 0–2 | `position_xyz` | World position, meters |
| 3–5 | `orientation_rpy` | Roll, pitch, yaw, radians |
| 6–8 | `linear_velocity_xyz` | m/s, world frame |
| 9–11 | `angular_velocity_xyz` | rad/s |
| 12–161 | `action_history` | The 25 most recent 6-dim actions (0.5 s at 50 Hz), oldest first, zeroed at reset |
| 162 | `altitude_norm` | Downward-ray ground clearance / 20 m, in [0, 1] (ray starts 0.03 m below drone centre; reads 1.0 when nothing is hit within 20 m) |
| 163–164 | `search_clue_offset_xy` | Clue centre minus drone position, XY only, meters, unbounded (see the clue rule below) |
| 165–213 | `teammate_rel_state` | 7 slots × [relative position (3, m), relative velocity (3, m/s), present flag (1.0 real / 0.0 padding)], nearest teammate first, ties broken by drone index |

**The search clue is noisy by design.** All drones share one clue centre, sampled uniformly in a disk around the victim's true XY position. The disk radius scales with team size:

```
radius = 80 · sqrt(n / 8)  meters      (40 m at n=2 … 80 m at n=8)
```

so the sweep area *per drone* stays constant. The clue carries no Z information. This team rule replaces the single-drone SAR 30 m clue.

## Actions

Per drone: `[dir_x, dir_y, dir_z, speed, yaw, rgb_request]`.

- **Velocity command**: `SPEED_LIMIT · |speed| · unit(dir)` with `SPEED_LIMIT = 3.0 m/s`, executed by the onboard PID controller. The validator additionally rescales `dir` by `min(1, 3.0/‖dir‖)` per drone before stepping.
- **Yaw** is an *absolute* target: `yaw · π` rad, slew-limited to 3.141 rad/s.
- **`rgb_request > 0.5`** requests an RGB frame for the *next* observation (subject to the 40-per-drone budget).

Actions are canonicalized by the runner: components are clipped to the bounds above and quantized to a fixed step. A NaN/inf or wrong-shaped output is an artifact fault that fails the seed; a timed-out step substitutes a zero action (a hover-in-place velocity command) and counts a strike.

## Maps

The family runs on five procedurally generated environment types (**warehouse is excluded**):

| Type | Environment | Benchmark slots | Start→goal distance band |
|---|---|---|---|
| 1 | City | 17 | 15–28 m |
| 2 | Open | 17 | 14–22 m |
| 3 | Mountain | 17 | 30–60 m |
| 4 | Village | 17 | 25–50 m |
| 6 | Forest | 16 | 15–31 m |

The benchmark template has 84 slots (the SAR 100-slot template minus warehouse), each type's band split into 3 distance sub-bands, no moving obstacles. The template repeats cyclically to fill the 800 full-benchmark seed positions. Each slot carries a fixed, deterministic drone count:

```
n_drones = 2 + (slot_index % 7)        # cycles 2..8
```

The distance band sets the start→goal pad geometry; the scored objective is the victim, placed independently (see below). On the open map the default ground plane is dropped away after world build: drones fly over the generated terrain, not a flat plane.

## Episode rules

| | |
|---|---|
| Control / physics rate | 50 Hz (`sim_dt` = 1/50 s) |
| Horizon | 60 s (up to 3,000 `act()` calls) |
| Drones | 2–8, one policy |
| Start | Each drone on its own 0.6 m-radius platform, level, 0.121 m above the pad top; pads placed deterministically, rejection-sampled for ≥ 4.0 m pairwise XY spacing (best-gap fallback if a map is too cramped) |
| Victim | One shared humanoid mannequin, ≤ 80 m XY from the first start pad (falls back to the nearest valid spot if no candidate within 80 m passes the surface checks), on an accepted support surface (slope and clearance checked); mesh scale 0.6 on city/village, 1.0 elsewhere |

### Success: the hover-confirm

The team succeeds the **first** time **any** drone holds all three conditions *continuously* for **2.0 s**:

| Condition | Bound |
|---|---|
| Horizontal distance to victim centre | ≤ 2.0 m |
| Speed (3D) | ≤ 1.0 m/s |
| Height above victim's bounding-box top | within [2.0, 4.0] m |

Once the dwell starts, a hysteresis grace of 0.1 (m and m/s) widens all three bounds so borderline jitter doesn't cancel a confirm. Leaving the widened bounds resets the dwell timer to zero.

### Failure

| Reason | Rule | Scope |
|---|---|---|
| `NO_TOUCH_SPHERE` | Any drone comes within **0.8 m** (3D) of the victim centre | **Fails the whole mission instantly** |
| `TILT` | \|roll\| or \|pitch\| > 1.047 rad (~60°) | That drone crashes |
| `OBSTACLE_COLLISION` | Any non-pad contact (touching the victim counts) | That drone crashes |
| `SPAWN_FAILURE` | Victim spawn pipeline exhausts its attempts | Whole episode |
| `TIMEOUT` | t ≥ 60 s with no confirm | Surviving drones |

Crashed (and confirmed) drones are **frozen in place as static obstacles**. The rest of the team keeps flying and must avoid them. The episode terminates on spawn failure, mission failure, team success, all drones frozen, or the horizon.

## Scoring

One team score, applied identically to every drone.

**On success:**

```
final = clamp01( 0.45 · 1.0  +  0.45 · time_term  +  0.10 · team_safety )
```

**On failure:** a participation reward of `0.01` if the team failure reason is one of `OBSTACLE_COLLISION`, `NO_TOUCH_SPHERE`, `INFEASIBLE`, `SPAWN_FAILURE`, `TILT`, `TIMEOUT`; otherwise `0.0`. (If the team reason is `TIMEOUT` but every drone individually crashed, the first crash reason is reported instead.)

### The time term

```
time_term = 1.0                                    if team_t ≤ target_time
          = clamp01( 1 − (team_t − target_time) / (horizon − target_time) )   otherwise
```

`team_t` is the confirm time. The target time budgets a fly-to-clue leg, a team-divided disk sweep, and the dwell:

```
target_time = 1.03 · ( d(start_centroid → clue_centre) / 3.0
                     + (0.70 · π · R² / (24.0 · 3.0)) / n_drones
                     + 2.0 )
```

with `R = 80·sqrt(n/8)` m (the clue-disk radius), sweep width 24 m, speed 3 m/s, dwell 2 s, and a 1.03 buffer. The sweep budget divides by the drone count: more drones are expected to find the victim proportionally faster.

### The safety term

`team_safety = 0.0` if **any** drone collided. Otherwise it is the mean over drones of the per-drone clearance term:

| Min clearance | Term |
|---|---|
| ≥ 1.0 m (0.6 m on forest) | 1.0 |
| ≤ 0.2 m | 0.0 |
| in between | linear |

Per-drone minimum clearance **excludes live teammates, the victim, the start pads, and the ground plane**: flying in tight formation never lowers the safety score.

## Runtime limits

Your zip runs as a Cap'n Proto RPC server inside Docker; the validator calls `ping()`, `reset()` between seeds, and `act(obs)` once per control step.

| Limit | Value |
|---|---|
| Zip contents | `drone_agent.py` at root with `DroneFlightController` (`act`/`reset`) + `swarm_policy_contract.json` |
| Uncompressed size | 50 MiB max |
| Forbidden suffixes | `.exe` `.so` `.dll` `.sh` `.bat` `.pyc` |
| Container resources | 6 GB memory, 2 CPUs |
| `ping` / `reset` timeouts | 2.0 s / 5.0 s |
| First `act` | 2.0 s budget, 3.0 s hard cap (reference time) |
| Per-step `act` | 0.6 s baseline-equivalent compute; hard cap 2.0 s reference + measured RPC overhead + 0.05 s margin |
| Strikes | 3 hard-cap strikes or 15 RPC timeouts fail the seed |

Timing is hardware-fair: your steps are judged in baseline-equivalent time, so a slower validator host doesn't penalize you. Package installs in the container are whitelisted: torch/torchvision/torchaudio, onnx/onnxruntime(-gpu), stable-baselines3, sb3-contrib, gymnasium/gym, swarm-bullet3, swarm-drone-gym, numpy, scipy, scikit-learn, opencv-python(-headless), pillow, imageio, matplotlib, pyyaml, tqdm, einops, tensorboard, h5py, msgpack.

Every submission goes straight to the full benchmark. (A screening phase with its own 41-slot template and early-fail checkpoints exists in the codebase behind an operator constant, currently disabled.)

## Local testing

Package, verify, and benchmark the same artifact with the family selected:

```bash
swarm model package --source ./my_model --family-id cf_swarm_sar
swarm model verify --model Submission/submission.zip
swarm benchmark --model Submission/submission.zip --family-id cf_swarm_sar --workers 4
```

`--seeds-per-group` controls seeds per environment group (default 3).
